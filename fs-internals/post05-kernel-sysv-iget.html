How the Linux Kernel Maps Inode Numbers to Disk Sectors (V6 vs. System V)

May 2026

The Problem

A classic challenge in filesystem implementation is mapping a 1-based logical inode number (e.g. inumber = 100) to its exact physical location on the storage media. On a Unix V6 filesystem, each inode is 32 bytes and sectors are 512 bytes, meaning exactly 16 inodes fit inside a single sector. With the inode table starting at sector 2 on the disk, how does the filesystem locate and extract a specific inode?

The Pedagogical Implementation (C/C++)

In our pedagogical Unix V6 filesystem simulator, we implemented this translation using straightforward arithmetic operations (division and modulo):

int block_of_inode = INODE_START_SECTOR + (inumber - 1) / INODES_PER_BLOCK;
int slot_in_that_block = (inumber - 1) % INODES_PER_BLOCK;

For inumber = 100, with INODE_START_SECTOR = 2 and INODES_PER_BLOCK = 16:

1. block_of_inode    = 2 + (100 - 1) / 16 = 2 + 6 = 8
2. slot_in_that_block = (100 - 1) % 16 = 99 % 16 = 3

This tells us that inode 100 sits at block 8, slot index 3 (the 4th slot, since arrays are 0-indexed).

The Production Implementation (Linux Kernel 6.8.0)

We searched the local Linux kernel source code on our machine and found the exact production counterpart inside fs/sysv/ialloc.c under the function sysv_raw_inode():

struct sysv_inode *
sysv_raw_inode(struct super_block *sb, unsigned ino, struct buffer_head **bh)
{
	struct sysv_sb_info *sbi = SYSV_SB(sb);
	struct sysv_inode *res;
	int block = sbi->s_firstinodezone + sbi->s_block_base;

	block += (ino-1) >> sbi->s_inodes_per_block_bits;
	*bh = sb_bread(sb, block);
	if (!*bh)
		return NULL;
	res = (struct sysv_inode *)(*bh)->b_data;
	return res + ((ino-1) & sbi->s_inodes_per_block_1);
}

Comparing the Mathematics

Although the Linux kernel code looks different at first glance, the underlying mathematical translation maps perfectly to our simulation, optimized for execution speed:

Step 1: The Base Sector Offset

Simulation: INODE_START_SECTOR (fixed constant 2)
Kernel: sbi->s_firstinodezone + sbi->s_block_base (dynamic superblock geometry parameters)

Step 2: Division by 16 via Bitwise Right Shift

Simulation: (inumber - 1) / 16
Kernel: (ino-1) >> sbi->s_inodes_per_block_bits (where s_inodes_per_block_bits = 4)
Equivalent: (ino-1) >> 4 is identical to integer division by 2^4 = 16.

Step 3: Modulo 16 via Bitwise AND Masking

Simulation: (inumber - 1) % 16
Kernel: res + ((ino-1) & sbi->s_inodes_per_block_1) (where s_inodes_per_block_1 = 15 or 0xF)
Equivalent: (ino-1) & 15 is identical to modulo remainder extraction % 16 because it isolates the lowest 4 bits.

Why the Kernel Avoids Modulo and Division: Integer division (DIV/IDIV instructions on x86_64) is a notoriously slow operation, taking 10 to 40 CPU clock cycles depending on the processor generation. In contrast, bitwise shifts (SHR) and bitwise ANDs (AND) are single-cycle, pipeline-friendly instructions that run with zero latency, making them mandatory in performance-critical hot paths like the filesystem block layers.
