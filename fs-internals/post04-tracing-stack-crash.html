#04

Tracing Stack Crash with Real Data: GPF vs. Page Fault

May 2026

The Premise

Returning a stack pointer from a C/C++ function is a classic undefined behavior bug. When the function returns, its frame is destroyed. If you call another function, it overwrites the stack memory. When the caller tries to dereference that corrupted pointer, a crash occurs. But exactly what does the silicon and the kernel do in this scenario? We set out to find out using real kernel probes (kprobes).

The Experiment

We wrote a buggy C program that allocated a local buffer on the stack, returned its address, called a stack-corrupting function garbage_stack(), and then attempted to dereference the corrupted pointer. We tested two variants of pointer corruption to see how the CPU and OS reacted.

Case A: Non-Canonical Address Corruption (GPF)

In the first case, we mangled the pointer to a completely invalid address: 0x5555555555555555. When we ran the program, the kernel immediately logged this in dmesg:

[ 3250.873323] traps: buggy[238340] general protection fault ip:760bd5d8b7dd sp:7ffc3ffad408 error:0 in libc.so.6[18b7dd,760bd5c28000+188000]

Silicon Mechanics: On x86_64, a virtual address must be in canonical form: bits 48 through 63 must be identical copies of bit 47. The address 0x5555555555555555 violates this rule. When the MMU attempts to decode a non-canonical address, it bypasses the normal page fault logic entirely and fires a General Protection Fault (GPF, Interrupt 13). The kernel's GPF handler directly kills the process by issuing a force_sig call.

Case B: Canonical but Unmapped Address Corruption (Page Fault)

In the second case, we set the corrupted pointer to a canonical user space address that is completely unmapped: 0x123456789000. This time, our custom kprobe placed at force_sig_fault captured the crash perfectly:

[ 3278.126297] buggy[238451]: segfault at 123456789000 ip 00007229c558b7dd sp 00007ffc38c6a4f8 error 4 in libc.so.6[18b7dd,7229c5428000+188000]
[ 3278.126331] KPROBE CRASH: force_sig_fault triggered by 'buggy' (pid: 238451)!
[ 3278.126336]   Signal: 11, Code: 1, Faulting Address: 0x123456789000

Silicon & Kernel Walk (Page Fault Scenario)

STEP 1: CPU MMU triggers Page Fault (Interrupt 14)

The address 0x123456789000 is canonical, so the CPU attempts to walk the 4-level page table. It finds no entry (PTE is not present). The CPU suspends the thread and generates a Page Fault (Interrupt 14), loading the faulting address into the CR2 register.

STEP 2: Kernel Exception Handler

The kernel catches Interrupt 14 in exc_page_fault(), which calls do_user_addr_fault(). It searches the process's active Virtual Memory Areas (VMAs) in find_vma(). It finds that 0x123456789000 is completely outside any valid allocated region.

STEP 3: force_sig_fault Call

Since the address has no VMA, the kernel calls bad_area, which ultimately routes to force_sig_fault(SIGSEGV, SEGV_MAPERR, 0x123456789000). This helper builds a signal info struct and delivers SIGSEGV directly to the process.

The Kernel Driver Code (kprobe_crash.c)

To capture this, we loaded a kernel module that registers a probe at force_sig_fault. It extracts registers from the hardware stack and logs the crash parameters to `dmesg`:

#include <linux/module.h>
#include <linux/kprobes.h>
#include <linux/sched.h>

static struct kprobe kp = {
    .symbol_name = "force_sig_fault",
};

static int handler_pre(struct kprobe *p, struct pt_regs *regs)
{
    if (strcmp(current->comm, "buggy") == 0) {
        int sig = (int)regs->di;
        int code = (int)regs->si;
        unsigned long addr = (unsigned long)regs->dx;

        pr_info("KPROBE CRASH: force_sig_fault triggered by '%s' (pid: %d)!\n",
                current->comm, current->pid);
        pr_info("  Signal: %d, Code: %d, Faulting Address: 0x%lx\n",
                sig, code, addr);
    }
    return 0;
}
Key Insight: Pointer corruption crashes behave completely differently depending on the virtual address. A non-canonical load causes an immediate General Protection Fault, bypassing page table walks entirely. A canonical but unallocated address forces a complete page table traversal before failing with a Page Fault.
